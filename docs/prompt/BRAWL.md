## 1. 一句话

**实时、自动、连续移动的两军对垒战棋——团灭判胜的"斗蛐蛐"。**
玩家不指挥战斗里的任何一只手：他在**轮次之间**决定"带谁上场、摆成什么阵、拿哪条强化、打哪支敌阵"，
然后看它们自己打。

它**不是**：
- 不是回合制战斗。那一套（`Phase` 机 / AP / END TURN / 脑子 HP）是 `PROMPT.md` §3.1 的另一条线，两条线**平行存在**。
- 不是塔防。没有"僵尸从右边一波波来"，两边是**对称的两支队伍**，各有自己的出生带。
- 不是花园或战役的一环。乱斗的棋子与花园里的植株是**两套东西**（§9）。

### 1.1 它像什么：金铲铲之战（2026-10-04 用户口径："大致按照金铲铲这个游戏实现游戏设计"）

以这一条为总口径（**D21**），把 TFT 的系统逐条对到本工程；**做 / 不做 / 待定**分三档（⏳ 的条目见 §11）：

| 金铲铲的系统 | 本工程对应 | 这一版 |
|---|---|---|
| 棋子（英雄）+ 费用 1–5 费 | 乱斗棋子（来源：植物 / 僵尸 / **人类**三个阵营）+ `费用` 列 | **做**（内容先少） |
| 人口上限 / 等级（买经验涨上阵人数） | **D16**：可上阵上限**起始 3**，靠奖励提升（不买经验） | **做** |
| 海克斯强化（三选一） | **D3 第 3 步**"选取随机强化" | **做** |
| 对手 / 敌阵 | **D3 第 4 步**"选取要挑战的敌阵"——**PvE 阶梯**，不是 8 人同局 | **做** |
| 棋盘半场 | **D11**：四方格 4 列 × 5 行，中间 1 列无人区 | **做** |
| 3 星合成（3 个同名 → 高一星） | 棋子的星级 | **不做**（留列，D24） |
| 羁绊（同族/同职业凑数触发） | ？ | **不做**（D25） |
| 商店 | **D22：三选一里的一种特殊事件** | **做**（但没有"刷新"这套） |
| 金币 / 利息 / 连胜奖励 | 会话内的钱 | **钱做**（商店要用，⏳ O24），利息与连胜**不做** |
| 装备（三件基础合成一件成装） | 乱斗**挂件**（装备 / 强化同构，见 §8.6） | **做**（**D42 推翻 D26**；"合成"那一半仍不做，见 O34） |
| 玩家血量（输了掉血，掉光出局） | ？ | **不做**：输了只是不给奖励（D23） |
| 选秀 / 共享棋子池 / 8 人同局 | — | **不做** |

## 3. 对局形状【已定】

- **两支队伍**：左边是玩家的阵，右边是敌阵；两边**各自半个场地**既是布阵区也是出生带（D11 / D12）。
- **胜负 = 团灭**：一方棋子全部倒下，另一方胜。**没有脑子 HP**。
- **一局 = 若干轮次**：每轮次 ≈ 2 分钟，一局目标 ≈ 60 分钟（⇒ 约 20–30 个轮次），**平铺、不做章节**（D18）。
- **每方场上上限 20 个棋子**（同时在场，不是总数）；**开局只能上 3 个**，上限靠奖励提升（D16）。

### 3.1 场地分区（D11 / D12）【已定】

```
列 0 ─ 3            列 4            列 5 ─ 8
┌────────────┬─────┬────────────┐
│  玩家的半场  │ 无人区 │  电脑的半场  │   每方 4 列 × 5 行 = 20 格
└────────────┴─────┴────────────┘   场地 = 9 列 × 5 行（照用 Balance.COLS / ROWS）
```

- **半场的 20 格 = 每方上限 20 个棋子**：一个棋子一个格位——这是 D6 与 D11 对上的算术结果，不是巧合。
- 两军最前沿只隔 1 列（96px）⇒ **开局几乎立刻接战**。2 分钟一轮的节奏需要它；
  以后若想让"接近"也有一段戏，动的是**无人区的宽度**（把中间留宽），而不是另开场地。
- **出生带 = 整个半场**（D12 / D28 已确认）：棋子在**摆好的位置**上就地生成，没有"走进场"这一步。

### 3.2 超时狂暴（D13）【已定】

2 分钟到了双方都没团灭，**不判点**，而是给**双方的战阵**同时叠一组越拖越强的效果：
**持续掉血 + 攻速提升 + attack提升 + 防御削弱**。

- 形状：一个随时间增长的"狂暴等级"，四个效果各自按等级取数值（数值归 `BalanceBrawl`，曲线见 O21）。
- 为什么是"双方一起狂暴"而不是加时：它把**僵局**（两个肉盾互相啃不动）变成**必然终止**的过程，
  而"必然终止"正是无头自检能验证的东西（§14）——加时只是把僵局拉长。
- **首版曲线（D30：AI 给的首版，手感再调）**：**2:00 触发**，之后**每 10 秒升 1 级、6 级封顶**；每级给**双方每个棋子**：
  **每秒掉 0.5% 最大 HP**（按等级叠：6 级时 3%/s）、**攻速 +10%**、**attack +8%**、**护甲 −8%**（乘法，下限 0）。
  照这组数，最迟 **3:00** 前后必然团灭 ⇒ 一轮次的真实时长落在 **2–3 分钟**。

## 4. 场地与移动【已定：四方格 9×5 + 自由浮点二维 + 避让】

- **棋盘照用现在这块**（`Balance.COLS=9 / ROWS=5 / CELL_SIZE=96`，D11 / O4）：`Grid` 的注册表、
  `cell_to_world()` / `world_to_cell()` 两个换算点、格子绘制、窗口适配**全部复用**。
  新事实只有一条：**哪半场归谁**（列 0–3 / 5–8）——`Grid` 现在有"启用哪些**行**"的机制
  （`set_enabled_rows()` / `is_enabled()`），把它**扩成"区域"**即可，这是 B1 的一处小活。
- **位置的真相是浮点二维坐标**（D2）——与"复用棋盘"不冲突：`Grid` 给的是**地址**，不是**位置**：
  棋子的 `col/row` 是 `world_to_cell(pos)` 的派生值，**跨格时才改登记**
  （`Zombie.relocate_to()` 那条"先注销、再移动、再登记"的纪律，在乱斗里每一步都要守）。
- **没有障碍物**（D14 / O5）⇒ **不需要 A***：目标选择 + 转向（steering）+ 分离（separation）就是"避让"。
  哪天有障碍物了再上流场（flow field）：9×5=45 格一张场、所有棋子查同一张，比 40 个 A* 便宜一个量级，
  而且天然长出"绕行"。
- **体积与碰撞**（D14 / O6）：半径 ≈ **0.4 格**；棋子之间**软推挤**（分离力），**不做硬阻挡**——
  硬阻挡在实时里会死锁，而死锁的表现就是"看着两个兵顶牛到超时"。
- **朝向**（D14 / O7）：朝向 = 移动方向；attack时转向目标（`human.tscn` 是带骨骼的小人，朝向画得出来）。
- **空间索引**：用格子分桶（`Grid` 的注册表就是桶），邻居只看周围 3×3 格——
  40 个棋子的分离检测从 O(n²)=1600 降到 O(n·k)。
- **棋子可以穿过自己人**（D31）：只有分离力、没有阻挡，"穿过"表现为**挤开**。

## 5. 时钟与行动（实时状态机）【已定：实时 + ⏳ 常数】

`PROMPT.md` §3 索引里写的"**3.1 回合状态机 + 连续状态机**"，后半节就是这里。

**回合制的状态机是全局的**（`BOOT → TURN_START → OPERATION → PLANT_ACTION → ZOMBIE_ACTION → TURN_END → WIN/LOSE`，`battle.gd` 的 `Phase`）。
**乱斗的状态机是每个棋子自己一台**，没有全局回合：

```
IDLE → SEEK（选目标）→ MOVE（寻路/避让）→ ENGAGE（进入attack距离）
     → WINDUP（前摇）→ HIT（命中）→ RECOVER（后摇）→ SEEK …
     任何状态 → DOWN（倒下）
```

**[B8] HIT 现在有两种形状**（§8.7）：近战**当场结算**，远程把它交给一发**真飞的射弹**，
落地才结算。状态机一个字没改，变的是**命中的时间**——而"一次attack的数值"仍在**出膛那一刻**算好
（`BrawlActor.blow_value()`），射弹只负责把它带过去。

- **定步长推进**：⏳ 建议逻辑 **20–30 Hz**、渲染独立（GDScript 的现实约束）。暂停与倍速只改"这一帧推几个 tick"。
- **AP → 速率**：回合制"每回合发 3 点 AP"在实时里变成"AP 随时间攒"，攒够 `threshold` 就出手。
  **表的语义一个字不变**（`skills.csv` 的 `技能消耗AP`、`zombies.csv` 的 `移动` 仍然是相对快慢），
  只多一个换算常量 **`ROUND_SECONDS`**（一回合 = 几秒）。⏳ 建议 **2.5–3s**：豌豆每 0.83–1 秒一发、
  普通僵尸每 7.5–9 秒走一格，一轮次 2 分钟足够分出胜负。
- **种子化**：会话注入 RNG，**不许直接调 `randf()`**；迭代顺序按坐标排序（照 `battle.gd` 的 `_sort_by_row_col()`），不依赖字典顺序。
  这条不是为了好看——**它是"实时"能被无头验证的唯一前提**（§14）。

## 6. 一局的循环【已定：D3 + D4；B2b / B2c 已落地】

**两个页面 + 一个场景**：**编排页**（整块战场 + 摆阵 + 在右栏切换敌阵）→「出战」→ **竞技场** → **结算页**（一局的结果）→「下一轮 / 重挑对手」→ 回编排页。

- **敌阵的选取在编排页**（用户 2026-10-04 的口径）：切换右栏的选项时，**敌方半场的预览跟着变**——"我要打谁"和"我怎么摆"是同一个决定，看着同一块棋盘做。

每一个**轮次**：

| 步 | 玩家做什么 | 形状 |
|---|---|---|
| 1–3 | **编排页**（B2c 已落地；**候战区 B5+ 重做**） | 整块 9×5 战场带网格：**左半场可编辑**（上阵数 ≤ **当前上限**，开局 3，D16），**右半场是当前选中敌阵的预览**，**右栏**是该轮的三/两个敌阵 + 商店（点一下就换，预览跟着变）。**候战区 = 战阵下面一排 9 个格位，每格与战阵格子同尺寸、并且正对自己头顶的那一列**：**拖动**棋子在自己半场与候战区之间搬动（落到已有棋子上 = 两者**交换**），**上场即离席**，**鼠标悬浮**任何一枚棋子都会弹出它的详情面板 |
| 4a | **战斗** ✅ | 实时自动；玩家只有**暂停 / 倍速**（D15）。己方阵容就是编排页摆的那一套（B2c 起，替身已下线） |
| 5a | **结算** ✅ | 胜 ⇒ 对手那格的**金币** + **三选一奖励卡**（棋子 / 强化 / 上阵上限 / 钱，D16）；**败 ⇒ 不给奖励，可重挑对手**（D23） |
| 4b | **逛商店** ✅ | 花**会话内的钱**买棋子 / 强化 / 上阵上限（§8.5）；离店即结束本轮（D22：一轮一次事件） |

再回到第 1 步，直到一局（60 分钟）的目标达成或玩家退出。

- **强化以"三选一"的形式出现**（D3 的"选取随机强化"）：它既是**战斗奖励**的一种，也是**商店的商品**。
  【B5 落地】胜局开出的三张卡里**必有一张强化**（三种卡互不重复），商店的货架上则是随机一件。
- **每轮次只有一次事件**（三选一挑一个），不是"打一场再逛一次店"。
- 【B5 落地】三选一里的**商店选项每轮恰好一个**（`BalanceBrawl.OFFER_SHOPS`），其余是战斗 —— 于是"这轮打不打"
  成了玩家的选择：挑商店就跳过这一轮的战斗（D22 的必然结果）。

### 8.1 表文件与属性清单（D19：**新开文件，暂不复用**）

原话："单位和物品等设计可以新开存储文件，而不是复用，**在我了解涉及哪些属性和数值后再考虑如何复用**。"
下面就是那份清单——**先看属性，再定复用**（怎么定见本节末尾的甲/乙）。

**一个棋子（piece）需要的属性**：

| 属性 | 为什么需要 | 现有表里有没有 |
|---|---|---|
| `name`（= id）、`名称`、阵营 `race` | 全工程引用它；植物 / 僵尸 / **人类** | ✅ `units.csv` |
| HP、attack、护甲 | 战斗 | ✅ `units.csv` + `zombies.csv` |
| 技能（代码/数值）、大招（代码/数值/充能） | 战斗 | ✅ `skills.csv` + `units.csv` |
| 费用 | 商店 / 奖励的价值 | ✅ `plants.csv` 的 `费用`（现在记的是阳光） |
| `svg` / `tscn` / rarity | 呈现 | ✅ |
| 脚本 | 行为 | ✅ `plants.csv` 的 `脚本`（P104 起是表列） |
| **攻速**（秒/次） | 实时战斗的节奏 | ✅ **人类**在 `humans.csv` 的 `attack间隔`；植物仍是 `技能消耗AP` + `ROUND_AP` 派生 |
| **attack距离**（格） | 近战 / 远程的分野 | ✅ **人类**在 `humans.csv` 的 `attack距离`；植物的 `range_cells` 仍写在**代码**里 |
| **移动速度**（格/秒） | 连续移动 | ✅ **人类**在 `humans.csv` 的 `移速`；僵尸仍是"`移动 3` = 3 回合走 1 格" |
| **星级**（1/2/3）+ 每星倍率 | 金铲铲的核心 | ❌（O15 决定要不要） |
| **羁绊标签** | 金铲铲的核心 | ❌（O16 决定要不要） |
| 站位/职责（近战 / 远程） | 编队页给人的提示 | ❌（可由attack距离派生） |

**道具（装备，O17）**：`分类`（基础 / 成装）、`合成材料`、`属性加成`（HP / attack / 攻速 / 护甲）、`特效`、`图标`、`价格`。
**强化（海克斯）**：`name`、`等级`（银 / 金 / 彩）、`效果种类`、`数值`、`作用域`（全场 / 某阵营 / 某棋子）。
**敌阵**：`name`、战力、奖励、阵容（棋子 id + 位置 + 星级 + 装备）。

**两种落法（O18 已定：甲）**：

| | **(甲) 挂进现有分层表**——`data/units/humans.csv` + 子族表 | **(乙) 乱斗自成一棵表**——`data/brawl/pieces*.csv` |
|---|---|---|
| 复用 | `UnitSheet` 分层装配、读表原语、`rarity` **全部现成** | 全都要重写一遍（或只借 `UnitCsvManager` 的读表原语） |
| 隔离 | 新列落在**新层**，不污染 `plants.csv` / `zombies.csv`（分层规则：一列只有一个业主） | 与回合模式**零耦合**，改坏伤不到战役 |
| 代价 | 门面要新增第三个读取者；"这一行属于哪个模式"靠 `race` 区分 | "同一个事实两份表"的风险（人类棋子在两个模式里各一行怎么办） |
| 结论 | ✅ **选甲**（本轮 O18 拍板）：**列分开、文件新开，本来就等于"新开存储文件"** | ✗ 不选（只有乱斗棋子与回合模式**彻底不同构**时才考虑） |

**乱斗道具（装备）本版不做**（D26）⇒ **不建这张表**；哪天要做，它与回合模式的道具（卷轴 / 药剂 / 宝箱）不是一回事，
所以那时也应当新开 `data/brawl/equipment.csv`，`data/items.csv` **不动**。

### 8.2 强化【已定形状；B5 落地】

- 形状照战役的 mod（`key / value`），但**数值与白名单是乱斗自己的**（**B7 起是 `data/brawl/gear.csv`** + `BalanceBrawl`——强化与装备同一张表，见 §8.6.5）。
- **禁止**复用战役的 `RUN_MOD_KEYS`：那是战役的业主，两个模式共用一张白名单等于"改战役会动到乱斗"。
- **【B5 落地】** 表是 `name / name_zh / 等级 / 效果 / 数值`，读者 `scripts/core/db/gear_db.gd`（`GearDB`，**B7 由 `augment_db.gd` 改名而来**）。
  五个效果键（`BalanceBrawl.AUGMENT_KEYS`）：**生命 / attack / 移速 / 攻速 / 受伤**。
  ⚠ **2026-10-04 起作用域改了**（D43）：不再是"乘在玩家那一侧的所有棋子"，而是**挂在某一个棋子上**
  ——形状见 **§8.6**（本节下面那句"全部乘在玩家一侧"按此作废）。
  等级 `silver / gold / prism` 决定**价格**与**抽中权重**（两条阶梯都在 `BalanceBrawl`）。
- **谁把强化变成数字**：`BrawlSession.augment_mods()`（**已由 `mods_for(index)` 取代**，§8.6.1）把**这一个棋子**
  身上的挂件按 key 求和 ⇒ `BrawlSetup` 那一行的 `mods` ⇒ `BrawlActor` 应用（血量在出场时、其余每次出手/每步）。
  **竞技场不知道"强化"是什么**，它只认 key 与增量。
- 首版七条：铁甲 / 利刃 / 疾行靴 / 快手 / 厚皮 / 战鼓 / 泰坦之血。

### 8.3 敌阵【已定形状】

- **落地形状（B2b）**：两张表，一个读者（`FormationDB`），与 `data/levels.csv` + `data/level/*.json` 同一套分工：
  `data/brawl/formations.csv`（名册：`name` / `name_zh` / `金币`，行序就是难度阶梯）+
  `data/brawl/formation_pieces.csv`（**一行一个可能上阵的棋子**：`formation` / `piece` / `col` / `row` / `概率`，整数格）。
  **【B8+】`概率` = 掷骰**（O43："敌阵概率出现可远程attack的单位"）：空 / 1 = 这枚棋子**一定**在那儿；
  小于 1 = **每轮掷一次**（`BrawlSession.roll_offers()` 用会话自己的种子 RNG）。
  ⚠ **一次掷骰、三处共读**：卡片上写的棋子数与强度合计、编排页预览的右半场、竞技场真正建出来的那一侧，
  读的都是**同一份** `offer["rows"]`（`BrawlSession.chosen_rows()`）——三处各掷一次就是三个不同的敌人。
  ⇒ 于是 `D34` 的"战力"变成**每轮都可能不一样**，这正是"概率出现"想给人的东西。
  ⚠ 两张表现在填的都是**替身棋子**（现成的植物与僵尸 id）：乱斗自己的 `data/units/humans.csv` 是 B5，代码不依赖出现哪些 id。
- 与 `data/level/Lawn_*.json`（波次 + 入场表）**同构但不是同一件事**：敌阵是一支**队伍**，不是一波敌人。
- **D32：敌阵不跟玩家的上阵上限走**——**游戏有自己的难度曲线**，敌阵是**编排出来的**（棋子数、棋子、站位都写在表里）。
  ⇒ 两个后果：① **敌阵必须显示可比较的"战力"**（⏳ O25），否则"自选"就是瞎猜；
  ② **"打不过"是玩家自己的判断失误**，代价按 D23：不给奖励、可以重挑对手（损失只是时间）。

### 8.4 奖励【已定：D16】

- 奖励进**会话**：**棋子**与**强化**都进池子。
- **上阵上限本身也是奖励的一种**：开局 3 个，靠奖励往上加（到 20 为止）。
- **奖励清单（首版）**：棋子 · 强化 · **上阵上限** · **钱**（§2.2 的推论：商店一旦存在就必须有货币）。
- ⏳ 奖励表要**同时喂两条线**（棋子种类 / 上阵上限），否则会出现"棋子一堆但只能上 3 个"或
  "上限很高但没棋子"——两者都是在浪费 60 分钟一局。
- **【B5 落地】** 胜局 = **对手那格的金币**（D4，自动进账）**+ 三张奖励卡挑一张**（`BalanceBrawl.REWARD_PICKS`）。
  四张卡的**种类**按权重抽，**互不重复**（棋子 / 强化 / 上阵上限 / 钱 各是一种），所以三张卡永远是三种不同的东西：
  抽到哪一件棋子、哪一件挂件由**各自的表**决定（`RosterDB` 的 `权重` 列、`GearDB` 的等级权重）——
  于是"奖励表要同时喂两条线"这件事由**加表行**完成，不另开一张奖励表。
  败局**一张卡也不开**（D23），平局同理。金币卡与上限步长是写死的两个数（`REWARD_COINS` / `DEPLOY_CAP_STEP`）。

### 8.5 事件与商店【已定：D22】

**每轮次的第 3 步是三选一**：从 **3 个选项**里挑 1 个。选项的种类：

| 事件 | 是什么 | 产出 |
|---|---|---|
| **战斗** | 一支敌阵（§8.3） | 胜 ⇒ 对手的金币 + 三张奖励卡挑一张；败 ⇒ 不给奖励、可重挑（D23） |
| **商店** | 花钱买棋子 / 强化 / 上阵上限 | 花掉会话内的钱 |

- ✅ **O24 货币 = 金币**（D33）：会话内、不落盘；来源 = 胜局（对手那格的 `金币` 列）**+ 开局的一小笔**
  （`BalanceBrawl.START_COINS` 10，够买最便宜的一档——不给的话"第一次三选一就挑商店"会是一屏买不起的东西）。用途 = 商店。
- ✅ **O26 三选一的生成 = 三个选项、至少一个战斗**（D35）：【B5 落地】实际是**两个战斗 + 一个商店**
  （`OFFER_COUNT 3` / `OFFER_SHOPS 1`），顺序由会话种子的 RNG 洗牌决定。
- **【B5 落地】商店的形状**：挑中商店后进**商店页**（`scenes/ui/brawl_shop.tscn`），**离店即结束本轮**。
  货架是**每轮一次**（与三选项同时掷出，所以走开再回来不会刷新），首版四个格子：**两件棋子 + 一件强化 + 一档上阵上限**。
  **价格全部来自表**：棋子 = `费用`（1–4 档）× `PIECE_PRICE_PER_COST`(4)；强化 = 等级阶梯（6/10/16）；
  **只有"上限 +1"这一档是写死的**（`SHOP_CAP_PRICE` 8）。⇒ "加一件商品 = 加一行表"在这三条路径上都成立。
- 与战役的路线图节点**同构但数据不共用**：战役是 `chapter_*.json` 里手写的分层图（`next[]` 是玩家选的路线），
  乱斗是**每轮次现生成的 3 个选项**（没有 `next`，做完就回第 1 步）。
- **输了不给奖励**（D23）；**货币**是 §2.2 的推论（⏳ O24 确认名字）。

### 8.6 装备与强化：挂件（attachment）【已定：D42–D45 是方向，D46–D55 是形状；**B7 已落地**】

**一句话：一个背包、一种挂件、三个槽。**

用户 2026-10-04 晚的口径（D42–D45）：**增加装备**；**把强化从"全队强化"改成"指定单位添加强化"**；
**数据写成 csv**；**编排战阵阶段加背包图标、把装备拖到单位上**；**每个单位 3 个装配槽**。
这一节写"怎么做"。**O32–O41 十条已由用户 2026-10-04 一句"全按推荐来"结掉**（逐条落成 D46–D55，
见 §2.1），所以本节里那些 ⏳ 现在都是**【已定】**——下标的"（O32）"只是把问题编号留个索引。

#### 8.6.1 一个原语：挂件（attachment）

- **挂件 = `{名称, id}`**，名称两种：`augment`（强化）/ `equipment`（装备）。
- **挂件长在棋子身上，不长在会话身上**：`BrawlSession.pool` 的每一项多一个 `attach: Array`，
  与 `col` / `row` / `slot` 并列 ⇒ **棋子被拖动时挂件跟着走**；`place()` / `send_to_bench()`
  换的是**位置**、不是挂件，那两个门的语义一个字都不用改。
- **"全队乘区"取消**：`BrawlSession.augment_mods()`（B5 的那一份）退役，换成
  **`mods_for(p_index) -> Dictionary`**——把这**一个**棋子身上的所有挂件按 key 求和。
- **数字仍在会话里合成、仍由 `BrawlActor` 应用**：`BrawlSetup` 的每一行从 `{piece, col, row}`
  变成 `{piece, col, row, mods}`，`Brawl._fill_side()` 把**这一行自己的** mods 交给那一枚棋子
  （`BrawlActor` 从 B5 起就是**每个 actor 一份 mods**，这一步只差把"一份"改成"一行一份"）。
  ⇒ **竞技场仍然不知道"强化"与"装备"是什么**，它只认 key 与增量；两种挂件在场上无法区分——
  这是设计目标，不是巧合（§12 那条"棋子的能力共用一份"在这里继续成立）。
- **敌阵将来也能带**：右侧的行走同一个字段。首版**留空**（**O41 = 留列不做**，同 D24 星级的处理）。

#### 8.6.2 槽位【已定：3 个 / 棋子】

- **`BalanceBrawl.ATTACH_SLOTS := 3`**：一个棋子最多挂 **3 件**；第 4 件要么替换、要么没地方放。
- ⏳ **O33：强化占不占这 3 格？** 推荐**占**（只有一种容量概念，UI 只画 3 个小格，
  强化与装备的差别就只剩"数值档 + 出处"）。备选：强化另有 1 格，两种各占各的。
- ⏳ **O36：挂上能不能取下来？** 推荐**能**（拖回背包即卸下，编排阶段随便换）。
  本模式是 PvE 阶梯、没有对手互动，"锁死"只会把一次误拖变成一整局的损失；
  TFT 那种"装上摘不下来"是为 8 人同局的博弈服务的，这里没有那个博弈。
- **同名可叠**：同一个 id 挂两遍就是两件（乘区各算一次）——与 `pool` 里可以有两枚同名棋子同一条规矩。

#### 8.6.3 背包【已定方向：D44】

- **会话多一个 `bag: Array`**（元素 `{名称, id}`，顺序 = 获得的顺序）。
- **获得 ≠ 装配**：奖励卡与商店买到的挂件**先进背包**，指派发生在**编排页**——
  买的时候看不见棋子（商店是独立一页），而"谁穿它"正是编排页要回答的问题。
  这是 D16 / D22 在挂件上的自然延伸，也让"三选一"不必多出一步。
- ⏳ **O38：背包画在哪、有没有容量上限？** 推荐**画在左栏**（那里现在是"对手卡 + 按键提示"两行，
  B5+ 从棋盘下面搬过去的）：上段留文字、下段放背包（一个背包图标 + 角标数字 + 若干挂件格）。
  **首版不限量**——挂件不占场上的格位，没有"满了怎么办"的第二次判定。真要上限，形状照候战区：
  满了就禁买（D41 的先例）。

#### 8.6.4 编排页的拖动矩阵【已定方向：D44】

页面已经有"按住 = 拿起、抬起 = 落下、位移不超过 `BRAWL_DRAG_THRESHOLD` 就当点击"的那一套
（B5+ 的棋子拖动）。挂件是**第二只手**，所以状态里多一个"手上拿的是棋子还是挂件"，两条手势互不干扰：

| 从 | 到 | 结果 |
|---|---|---|
| 背包格 | 棋子（自己半场或候战区） | **装上**：进第一个空槽；3 格满了 = **拒绝并说明**（O37） |
| 背包格 | 背包格 | 背包内排序（没有规则后果） |
| 棋子的一个槽 | 背包 | **卸下**（O36：**挂件永远取得下来**，没有"锁死"这一档） |
| 棋子的一个槽 | 另一个棋子 | **转移**：目标有空槽就进空槽，没有就与指针指着的那个槽**对调** |
| 棋子（不是槽） | 任何地方 | 仍是 B5+ 的**棋子**拖动：换位置，**挂件跟着棋子走** |

- **槽是画在棋子格上的三个小方块**（`cell` 底边一条）：指针落在第 k 块上就是第 k 个槽——
  "转移 / 交换"要能指名一个槽，光知道"落在棋子上"不够。落在棋子身上但没落在方块上 = **第一个空槽**。
- **图标**：挂件的图沿用 `UiStyle.draw_icon`（表里的 `svg` 列）；等级（银 / 金 / 彩）画一个**代码画的角标**
  ——和宝箱的辉光、rarity的颜色同一条思路：**颜色与角标由代码画，不进素材**（`PROMPT.md` §7.1）。

### 8.7 射弹与反馈【B8 已落地，2026-10-04】

**一句话：远程棋子的一次attack = 一发真的飞出去的射弹，命中才结算伤害。**

用户 2026-10-04 点单："增加观赏性，增加火枪射弹和弓箭射弹及其视觉听觉反馈。"

#### 8.7.1 谁射什么：一格表

- **射弹表仍是 `data/projectiles.csv`**（回合制那张，P91）：新增两行 **`arrow`（箭）** 与
  **`musket`（火枪弹）**，两者 `轨迹` = **追踪**、`外观` = `arrow` / `musket`、
  两条 cue = `bow` / `arrow_hit` 与 `musket` / `musket_hit`。
  `外观` 是封闭清单，所以 `ProjectileDB.LOOKS` 跟着长了两个成员——**"箭长什么样"只有一个业主**。
- **哪个棋子射什么 = "它的描述说它会发射弹"**（O42）：
  - **人类棋子**写 `data/units/humans.csv` 的 `射弹` 列（新列）：`archer → arrow`、
    `gunner → musket`，其余四个与 `default` 行是 `—`（近战）。
    ⇒ **"把一枚棋子改成远程" = 改一格表**，不是加一条代码分支。
  - **植物**走它自己的 `ShooterPlant.shot_id`（"发射 1 颗豌豆"的豌豆射手答 `pea`、
    寒冰射手答 `snow_pea_shot`、投手答 `cabbage` / `melon`）——**"它会不会射击"在两种模式里是同一个事实**。
    卷心菜、向日葵、樱桃炸弹这类**非射击**植物没有这个方法，于是它们挥击（走到attack距离内直接结算）。
  - **僵尸**：`zombies.csv` 里**没有一种远程僵尸**（全是"啃食"），所以僵尸在乱斗里一律近战。
    哪天加了一种会扔东西的僵尸，给它一个 `brawl_shot_id()` 就行，`BrawlActor` 一个字不用改。
- **射速**：表的 `速度` 列是**回合制的像素**，乱斗的坐标是**格**，所以
  `BrawlShot.speed_cells()` 用 `Balance.CELL_SIZE` 换算（箭 620 px/s ≈ 6.5 格/秒、
  火枪弹 950 px/s ≈ 9.9 格/秒）。**故意比豌豆（1100 px/s）慢**：豌豆要横穿整块草坪，
  而这里的飞行是要**被看见**的——弓手 3 格射程 ≈ 0.46 秒、火枪手 2.5 格 ≈ 0.25 秒。

#### 8.7.2 伤害只有一个业主【D58】

- 出膛那一刻，**射手把这一击算成数**（`BrawlActor.blow_value()`：自身attack + 狂暴的两条进攻项 +
  自己的attack挂件），**射弹只是把它带过去**。
- 落地时由 **`BrawlActor.land_hit()`** 结算——**和近战挥击走的是同一个门**，
  所以狂暴与挂件不会长出第二个业主。受害者自己的书（`厚皮` 的 `taken_mult`）在**落地时**才乘，
  因为它在飞行途中还可能变。
- ⇒ 射弹是**延迟**，不是第二张伤害表（§12 那条禁令在这里继续成立）。
- **[B11c/D88] 一条公式管全部：`hurt = attack × 128 / (128 + max(0, 防御))`**（`docs/NUMBERS.md` §3 是
  公式的业主：刻度 `DEFENCE_SCALE = 128` 就是“减半点”）。它跑在 **`Unit.take_damage()`** 里，
  所以乱斗的**四条命中路径（近战 / 射弹 / 光束 / 吞噬）一行都没改**就都带上了防御；
  `defence` 是 `units.csv` 的**共用列**，**基础值 20**（各族 `default` 行）、**盾卫自己写 50**（约 28% 减伤）。
  **防御 0 = 不减伤**，所以这一列对没填防御的单位是零影响。
- **[B12] 每一击都冒一个伤害数字**：在 `land_hit()` 里读 `take_damage()` **前后**的 hp 差——
  那是唯一知道“这一击最后被谁改了”的地方（无敌 / 防御 / 护甲 / 处决），所以漂字说的就是
  **血条真的掉了多少**。⛔ **狂暴的持续掉血不冒字**（它不走 `land_hit`）：一秒几下的百分比流血会把屏幕糊住。
- **射弹不绑定泳道**：乱斗没有行，碰撞是**真正的二维**（点到线段的距离，不是回合制那个"同一行"的窗口）。
- **三条轨迹在乱斗里各按自己的语义飞**（O44 拍板：**打空就让它打空，这种削弱算游戏特色**）：

  | 轨迹 | 乱斗里怎么飞 | 打空会怎样 |
  |---|---|---|
  | **`追踪`** | 每一步重新瞄准（目标死了就保持最后的航向继续飞） | 撞上别人就打在别人身上；飞出场外**消失** |
  | **`直线`** | **出膛方向固定不变**——所以**会走的目标躲得开** | 出场地边缘**消失**（`反弹` > 0 才弹一次再飞） |
  | **`抛射`** | **越过中间所有人**，只在落点找目标（弧线只是画出来的，地面航迹才是判定） | 落在空地上就**消失** |

  ⇒ **"打空就是打空"**：没有伤害、没有命中音、没有爆环、**也没有日志行**（豌豆一秒三发，日志会被淹）。
  命中第一个人的规则与回合制一致：**瞄准的那个必中，别人看 `穿透`，穿透用完就掉在第一个站着的人身上**；
  `穿透伤害` 决定被穿过的人挨不挨打，`溅射` 决定落点周围的人挨多少。

#### 8.7.4 射弹归竞技场所有

- `BrawlShot` 是 `BrawlField` 的子节点（和棋子同一个坐标系），**由 `Brawl` 持有、tick、清理**：
  棋子的 tick 只负责"我要开火了"，射弹的生死跟着这一局（重开、终局都清空）。
- **没有 `class_name`，按路径 preload**（ProjectileDB 的老规矩）：新全局类对 `--headless` 是隐形的。
- **飞行有安全网**：`SHOT_MAX_SECONDS` = 4 秒，飞不到就报一行日志并消失——
  否则"目标走出场地"或"表里速度写成 0"会留下一发永远飞着的箭。
- **射弹归竞技场所有**的另两条：`Brawl` 持有 / tick / 清理（重开与终局都清空）；
  `BrawlShot` 挂在 `BrawlField` 下（与棋子同一个坐标系）。飞行有 4 秒安全网，
  飞不到就报一行 `[Shot] … never arrived - dropped`——那是"表里速度写成 0"或"目标走出场地"的兜底，不是常态。

### 8.8 近战特效：图画写在单位的表行里【P110e 已落地，2026-10-05】

**一句话：一次近战留下的那张图画，是attack方自己的事——写在它的表行里，不由场地按"它是不是僵尸"去猜。**

用户原话："为民兵、骑士和队长也引入近战attack特效，分别指定 slash.svg / slash_heavy.svg /
slash_divine.svg。近战attack特效似乎应当绑定特定的近战attack技能。在相关 csv 中完成数据指定，并在代码中调用。"

- **表**：`data/units/humans.csv` 新增 **`近战特效`** 列（短名，指向 `assets/svg/fx/`）——
  `militia → slash`、`knight → slash_heavy`、`captain → slash_divine`；**其余留空 = 只出火花**
  （盾兵是故意的）。它是 `射弹` 列（D57）的**孪生兄弟**：一个说"这一击飞出去的是什么"，
  另一个说"这一击在落点留下什么"。
- **僵尸那半边**：`data/units/zombies.csv` 新增同名列，**只在 `default` 行写 `claw`**——
  "所有僵尸都抓"因此是**一格**，不是 44 行；某个名称哪天换花样，就在它自己那一格写。
- **一条链，四步**：表 → `PieceDB.melee_fx` / `ZombieDB.melee_fx` → **`Unit.melee_fx_id()`** →
  `Fx.spawn_melee_fx(id, at, facing)`。**门在身体上、不带 `brawl_` 前缀**：回合制僵尸的 BITE
  问的是同一句话（`HumanPiece` 的另外四道门才是乱斗专属的）。
- **场地不猜**：`_begin_strike()` 里原来的 `if unit.is_zombie` 没有了——竞技场只问身体，
  身体读自己的表行。**新棋子要新斩击 = 一个 CSV 格子**，代码一行不改。
- **图画归 `Fx`**（棋盘上的一次性画面），**不是**第七节那套具名姿态特效：判据是**寿命**，
  见 `docs/prompt/FX.md` §1。
- **近战仍然人人有火花**：图画是**加在**火花上的，不是替代它——没点名的人不会因此什么都不出。
- **远程不在这一列**：射弹命中画自己的爆环（§8.7.3），箭矢留下斩击是讲错了故事。
- ⚠ **名字写错不报错**：图画不出来、打击照旧结算，`UnitArt.warn_once` 只喊一次；
  排查的第一站是开机那行 `[Data] pieces: … %d with a 近战特效`。

### 8.9 怪兽阵营与三种远程attack【P110f 已落地，2026-10-05】

**一句话：三个远程单位，一次attack"不飞"——它在同一帧落到目标身上（hitscan），画面上留下一条连接两个身体的光。**

用户点单："为乱斗模式增加3个单位，来自怪兽阵营，分别是激光眼、火焰眼、眼球塔。attack方式分别为瞬发光束、
喷射火焰和连续冲击光束。单位的素材分别是 monsters/laser_eye.svg flame_eye.svg laser_eye_tower.svg。
需要为这3个单位的attack方式分别实现对应的远程attack特效。"

**① 一个阵营 = 一行 `races.csv` + 一张族表 + `PieceDB.FACTIONS` 一行**

| 表 | 加了什么 |
|---|---|
| `data/units/units.csv` | 三行（race `monsters`）+ 一行 **`默认怪兽`**（**`turned=0 / timed=1`**：这一族只进经典（乱斗）模式，不进回合模式） |
| `data/units/monsters.csv`（**新**） | 族表：`费用 / attack距离 / 移速 / attack间隔 / 射弹 / 近战特效 / 远程特效` |
| `data/units/races.csv` | `monsters → laser_eye` |
| `data/brawl/roster.csv` | 三行（都在候战席，权重 5 / 5 / 2）⇒ **商店与选卡里能抽到** |
| `PieceDB.FACTIONS` | `monsters` 一行（族表 + `assets/svg/units/monsters/` + 场景根） |

**② attack形状现在有三种，按这个顺序问身体**（与 `PieceDB` 读那两格的顺序一致）：

| 表里的格子 | 形状 | 谁结算 | 画什么 |
|---|---|---|---|
| `射弹` | 飞出去的东西 | **落地**时 `land_hit` | `BrawlShot` 自己的爆环 |
| **`远程特效`** | **不飞**（hitscan） | **同一帧** `land_hit` | **`Fx.spawn_beam` 画一条连接两个身体的光** |
| 两格都空 | 近战 | 同一帧 `land_hit` | 火花 + `近战特效`（§8.8） |

**③ 三张画**（`BalanceUI.BEAMS` 一张表，读者只有 `Fx.BeamLance`）：

- `laser` / **瞬发光束**：0.14 秒的一道细光，三遍叠画（晕 / 身 / 白芯）。
- `flame` / **喷射火焰**：0.30 秒的**锥**，七个三角火舌，**够不到目标中心**（只填 0.90 的间距）——
  这是它一眼可辨的地方。
- `impulse` / **连续冲击光束**：0.42 秒的粗光柱 + 四个**向外跑的亮环**，"连续"画在这里。

**④ 一条必须写下来的边界：光柱不追人。** 两个端点**只在生成那一刻取一次**，之后不跟身体走。
理由与 D61 同源（"直线弹按出膛方向飞，会走的目标躲得开"）——追人的光柱是同一个问题的第二套更聪明的规则；
而且 `Fx` 不持有 `Unit` 引用（图画要能活过它画的那个身体，施法者可以在光没灭时死掉）。
**觉得飘就先缩短时长，别先加跟踪。**

**⑤ 连续冲击光束是真的持续伤害【P110g】**：`持续` 那一格**有数**就成了一条**通道**——
开火那一帧先吃一次 `land_hit`，之后每 `BEAM_TICK_SECONDS`（0.5 秒）一跳、每跳
`blow_value() × BEAM_TICK_SHARE`（半个attack）——3 秒的通道是 **6 次命中（开火 1 + 通道 5）
= 3 次attack的量**（0.75 次/秒，与激光眼的 0.71 次/秒同档）。
**收尾判断排在跳之前**，所以边界帧不会多打一次，这个数**可以精确算**而不看帧率。**`持续` 空着就是一闪**（激光眼、火焰眼），
所以"一闪 / 通道"是**一格数据**的区别，不是两套代码。

- **"间歇 1 秒"不是第二个数**：`attack间隔` 就是**整个周期**——`4.0` = 烧 `3.0` + 停 `1.0`。
  所以 3 秒通道与 1 秒间歇是同一行的两格，改任何一个都要看另一个。
- **两条规则数在 `BalanceBrawl`**（`BEAM_TICK_SECONDS` / `BEAM_TICK_SHARE`），不在 `BalanceUI`：
  它们决定这座塔值多少钱。画面只读 `BalanceUI` 那三个（起手 / 收尾 / 亮环速度）。
- **通道节点归竞技场**（`Brawl.beams`，照 `BrawlShot` 的样子）：它要**跟着两个身体跑**、
  要在任一方倒下时收手、要随这一局一起清掉。所以它**不是** `Fx` 那种一次性的画——
  那种画刻意不持有 `Unit`（图画要能活过它画的那个身体）。
- **目标死了会转火**到最近的敌人（否则半秒打死人的 3 秒通道要白烧两秒半）；
  **自己死了立刻断**（眼球塔正是挨打的那个）；**一只眼不能同时烧两个目标**——
  `can_strike` 与 `open_beam` 两道门都问 `is_channelling`（狂暴会缩短 `attack间隔`，
  所以"计时器没到"这一道门挡不住它）。

**⑦ 一个"持续的火"不用一行代码【P110h】**：新单位 **火焰眼球塔**（`flame_eye_tower`，素材
`assets/svg/units/monsters/flame_eye_tower.svg`）= `远程特效 = flame` + `持续 = 3.0` +
`attack间隔 = 4.0`——**与眼球塔共用同一套通道、同一条间歇**，只是把"光柱"换成"火锥"。
所以 D83 那条通道**不是给眼球塔开的后门**，它是第三种attack形状的**通用能力**：
`持续` 有数就是通道，`远程特效` 说烧的是什么画。唯一跟着改的是**相速度**（D84）。

**⑥ 一处已知缺口**：`timed=1` 让这三个单位进了"这个模式引进的单位"的计数，但**经典图鉴的种族按钮只有
植物 / 僵尸 / 人类三个**（`brawl_almanac.gd` 的 `RACE_*`），所以**图鉴里暂时看不到怪兽这一页**。
补它是 UI 活（新页签 + `BalanceUI.ALMANAC_TAB_COUNT`），列在 `docs/STATE.md` §1 的下一批候选。

### 8.10 击退：把被打中的单位推开【B9 已落地，2026-10-05】

**一句话：盾卫的盾击不只是伤害——它把目标推开 1 格。“推多远”是族表里的一格，“怎么推”是竞技场的规则。**

用户原话：“乱斗模式将盾兵技能更改为将1个敌人击退1格的效果，从这里开始为游戏引入对单位的击退效果。”

**① 表：`击退` = 格数（它是 `射弹` / `近战特效` 的第三个孪生）**

| 表 | 加了什么 |
|---|---|
| `data/units/humans.csv` | **`击退`** 列：`shieldman → 1`，其余五枚留空 |
| `data/units/monsters.csv` | **同名列**（全空）：两张族表**列集相同**，读者才不会为缺列报警（`UnitCsvManager._check_column`） |

- **空 = 这一行不推**，不是“先去问默认行再说”：`PieceDB.knockback()` 是这条规则的唯一读者，`0` 就是答案。
- 单位是**格**、不是开关：将来“盾击推 2 格”与“推 1 格”是**同一行的两种写法**，不是两条代码路径。

**② 一条链，四步**：表 → `PieceDB.knockback` → **`HumanPiece.brawl_knockback_cells()`（第八道门）**
→ `BrawlActor.knockback_cells()`，结算由 `land_hit` 交给 `shove_from()`。

植物与僵尸**没有这道门**（`has_method` 答 false = 0），所以“乱斗里谁能推人”今天完全由族表决定：
给某一行写个 1，它就会推——**代码一行不改**。

**③ 规则（`BrawlActor.shove_from` / `_advance_shove`）**

1. **方向 = 背离打我的那个身体**（`pos - p_source.pos`；两个身体完全重合时用attack者的 `facing`）。
   这就是“来路”在二维里的唯一读法：侧面挨打成立，盾卫打盾卫也成立。
2. **距离是表里的格数，当预算花**：`shove_from` 只**上膛**，受害者自己的驱动每 tick 走
   `BalanceBrawl.SHOVE_CELLS_PER_SECOND`（6 格/秒 ≈ 一格 0.167 秒）。
   **故意不做瞬移**：实时里“中间那几帧”才是常态，一格瞬移会是这个模式里唯一跳过中间过程的位移。
3. **被推的那一 tick 不走路、不出手**（`tick()` 里那一段提前 return），但**attack计时照走**——
   被拿走的是地盘与一拍，不是已经付过的冷却。
4. **推不出场地**：仍然过 `BrawlField.clamp_to_arena()`；贴着墙的身体被顶住、预算照花完，
   不会一直顶着墙用力。
5. **连推叠加**：两个盾卫打同一个身体 = 推 2 格，**方向取最后一击的**（预算可以相加，“往哪边”只能有一个答案）。

**④ 只推活人，而且排在伤害之后**：`land_hit` 先结算伤害、再问 `击退`。被这一击打死的不推——
`take_damage()` 返回时死亡信号已经发过、`play_death()` 已经在放了，`shove_from` 的 `is_alive()` 门就是这一条。

**⑤ 反馈只有一个后仰**：被推的身体播 `UnitFx` 的 `hit`（具名姿态：后倾 + 后退；**后退那一半在乱斗里本来就失效**——
`Unit.shake()` 拒绝没有网格的身体，见 `docs/dev/FX.md` §4），`play_fx()` 是唯一那道门。
**不新增图画、不新增 cue**：P59 给回合制击退写的判词（“也不做被击退的独立反馈”）在这里照旧成立，
而且乱斗还没有观众 HUD（B4），加一条只在日志里看得见的反馈不划算。

**⑥ 它与回合制那个击退是“同一件事的两种世界”**：回合制的 `Zombie.push_back`（P59）同样“立刻结算、
不留计数器”，但**在那里“退”是列号变大**（泳道是方向，僵尸只往一边走），这里没有泳道也没有“左”（§12）。
所以两者**共享语义、不共享实现**——与 `BrawlIntent` 对“谁是最近的敌人”的分工是同一条理由。

**⑦ 两笔记账**（登记在 `docs/OPEN_ITEMS.md` §0.8）：① 乱斗里**只有被推的**身体会后仰，普通挨打仍然只是红闪——
要不要给“所有挨打”一个统一反馈是行为决定；② 击退**没有自己的图画与音效**，要加就是 `Fx` 一族 + 一条 cue。

### 8.11 吞噬：把敌人吞进肚子里消化【B10 已落地，2026-10-05】

**一句话：绿史莱姆碰到谁就把谁收进身体里——目标在它肚子里，看得见、持续掉血、什么也做不了；
消化时间一到还活着就被吐出来，把史莱姆打死就提前放人。**

用户原话：“为游戏添加green_slim绿史莱姆，素材是monsters/slim/green_slim.svg，为游戏引入特效吞噬。
绿史莱姆可以将敌人吞入自己的身体，然后进入消化阶段，消化阶段可以看到被吞噬的对象在史莱姆体内并持续扣血。
敌人在史莱姆体内无法行动和attack。”

**① 表：`吞噬` = 消化秒数（第四种attack形状的开关键）**

| 表 | 加了什么 |
|---|---|
| `data/units/monsters.csv` | **`吞噬`** 列：`green_slim → 6.0`，其余四行留空 |
| `data/units/humans.csv` | **同名列**（全空）：两张族表列集相同，读者才不会为缺列报警（`UnitCsvManager._check_column`） |
| `data/units/units.csv` | 绿史莱姆一行：race `monsters`、`svg = slim/green_slim`、`技能 = 吞噬`、`特殊机制` 写清楚“吞进去之后怎样”（**不写秒数**：那个数只有一个业主） |
| `data/brawl/roster.csv` | 一行（候战席，权重 3）⇒ 商店与胜局奖励里抽得到 |
| `scripts/core/loc_names.gd` | `piece.green_slim` = 绿史莱姆 / Green Slim |

**② attack形状从三种变四种，顺序就是 PieceDB 读这些格的顺序**：`射弹`（飞出去）→ `远程特效`（不飞，画一条光）
→ **`吞噬`**（不造成接触伤害，目标进肚子）→ 两格都空 = 近战。一行同时写了两种，先读到的那个赢。

**③ 一条链，四步**：表 → `PieceDB.gulp_seconds` → **`HumanPiece.brawl_gulp_seconds()`（第九道门）**
→ `BrawlActor.gulp_seconds()`，`_begin_strike()` 把这一口交给 **`Brawl.swallow()`**。
**被拒绝的吞噬会退回近战**（同一帧被别人先吞了、或自己嘴里还有东西）：会咬人的史莱姆，好过一击什么都不做。

**④ 被吞进去的那几秒（`scripts/core/brawl/brawl_gulp.gd`，竞技场持有的一张列表）**

1. **接触不掉血**：吞噬**取代**那一击，伤害改成在肚子里按时辰发——每 `BalanceBrawl.GULP_TICK_SECONDS`（0.5 秒）
   走**吞噬者自己的 `land_hit()`** 打一下，每下 `blow_value() × GULP_TICK_SHARE`（1.0 = 一个整attack）。
   所以狂暴、挂件、猎物的 `厚皮`、盾卫的击退，全都还是那一扇门（§12）。
2. **猎物的“不能行动”不在那个对象里**：它写在 `BrawlActor.tick` 的一行上——`held_by != null` 时只做一件事：
   **`pos = held_by.pos`**（跟着肚子走）。走路 / 转身 / 出手都排在这一行之后，所以全都不会发生。
3. **它也不在场上**：`is_swallowed()` 是**瞄准、分离力、射弹扫掠、光束转火**四处循环问的唯一一句话——
   肚子里的身体既不能被选为目标，也不能被箭穿过（那支箭会打在**吞了它的那个身体**上）。
4. **三种结束**：猎物死在里面（`died` → 照常结算与播报）；**消化时间到**（`吞噬` 秒）；
   **吞噬者死了**（`_alive(_slime)` 为假）。后两种都走 `release()`——**活着出来**，回到它自己的驱动手里。
   ⚠ 第三件是这套效果的博弈点：**打死史莱姆能把队友捞回来**，所以它是一个“要么快点杀、要么别被咬到”的威胁。
5. **消化期间吞噬者不能出手**（`BrawlActor.can_strike` 问 `arena.is_digesting(self)`，与眼球塔问 `is_channelling` 同一形状），
   **但可以走**：嘴里有东西的史莱姆照样移动，它只是没空再咬一口。

**⑤ 观感：猎物被画在肚子里**（`BalanceUI.GULP_*`，姿态归 `BrawlActor._apply_belly_pose`）——三件事一起做才算“在里面”：
**缩小**（`GULP_PREY_SCALE` 0.5）、**染成周围身体的颜色**（`COLOR_GULP_PREY`，自带 alpha）、
**画在本体之上**（`GULP_PREY_Z = 1`）。第三条是硬要求：史莱姆的画是一块**不透明**的色块，猎物画在它背后就等于看不见。
进肚子的那一帧还播一次 `hit`（被吞的身体也会后仰），落点出一个火花（`Fx.spawn_spark`）。
**尸体不还原姿态**：`play_death()` 一旦开始，淡出与缩小归它自己管。

**⑥ 它不带自检**（AGENTS §2）：机器读数只有开机那行 `[Data] pieces: … %d with a 吞噬`，验收见 §14。

### 8.12 升星：三个一样 ⇒ 升一星，三维 ×2【规则已定，**代码未落地**】

**一句话：同一个棋子凑够三个就合成一个、星级 +1，三维（生命 / attack / 防御）各 ×2。**

用户原话（2026-10-05）：“设定升星机制说明，每次升星需要3个相同单位，升星后三维数值各*2。”

- **公式**：`属性(星) = 基础值 × 2^(星-1)`（1★ = ×1、2★ = ×2、3★ = ×4）。**只乘三维**——
  攻速 / 射程 / 移速 / 费用 / 冷却一样都不动。乘法顺序是 `基础值 × 星级 × 挂件 × 狂暴`，
  所以星级与挂件互不干扰（都是乘算）。
- **合成**：同 id 的三个 ⇒ 星级 +1；**三个 2★ ⇒ 一个 3★**，照此类推；**上限 3★**（首版，D21 的形状）。
- **它是乱斗自己的轴**：棋子来自商店与胜局奖励，**同名才可能凑够三个**；花园植物走的是**等级**
  （`docs/NUMBERS.md` §4），一个单位不会同时吃两条成长。
- ⚠ **今天只有规则**：表里没有“星级”列、`BrawlSession` 不管合成、编阵页不画星。落地是三件事
  （登记在 `docs/OPEN_ITEMS.md` §0.8）：
  ① 棋子池与候战区的每一条记录带一个 `star`；
  ② 得手之后自动检查“同 id 满 3 个 ⇒ 升星”（递归到 3★ 为止，并**腾出候战区格位**——三个变一个，
  D41 的“候战区满 9 格”会因此松动，那条规则要跟着看）；
  ③ 三维按 `2^(星-1)` 施加在**现算数值**那一层（`HumanPiece.apply_piece` / `BrawlActor.setup`），
  与 §8.11 之前的“新增维度”同一个位置。
- **数值的业主是 `docs/NUMBERS.md` §5**（星级表与刻度在那里），本节只记规则。

### 8.13 能量与大招：把一次attack攒成一次爆发【B14 已落地，2026-10-06】

**一句话：有的棋子一次attack不只是那一下——它每打一下攒一笔能量，攒满了就放出一次大招；
而“大招”在乱斗里不是第五种attack形状，是这一行自己的那条光束被**按住不放**。**

用户原话：“为乱斗模式引入单位thundercorn，雷角兽，素材monsters/thundercorn.svg，面朝左侧。
攻击方式为从左上角的雷角得到电击，大招为连续电击3s。其每次普攻获得10能量，积攒100能量后释放大招。”

**① 表：`大招持续` = 大招按住几秒（它同时是“有没有大招”的开关）**

| 表 | 加了什么 |
|---|---|
| `data/units/monsters.csv` | **`大招持续`**：`thundercorn → 3.0`；其余四行留空（= 没有大招） |
| `data/units/humans.csv` | **同名列**（全空）。⚠ 这一批**顺手补齐了 humans.csv 缺的两列**（`远程特效` / `持续`，见 §8.9 与 §8.11 之后一直落下的一笔）：两张族表**列集必须一致**，少一列会被 `UnitCsvManager._check_column` 记成 complaint，而那个 complaint 会挂在**下一个跑自检的模块**（`[Plants]`）头上变成红 |
| `data/units/monsters.csv` / `humans.csv` | **`朝向`**：`thundercorn → 左`；两张表的 `default` 行写 `右`。它说的是**这一行的画朝哪边**，不是“它站哪边”。⚠ **[B16] 把这一列搬走了**：它现在是 **`units.csv` 的 `face` 列**（“这个身体的画朝哪边”是**单位**的事实，不是乱斗的）——见 **§8.15**。两张族表的那一列已经删掉，`[B14]` 的旧路径（`PieceDB.drawn_left`）随之退休 |
| `data/units/units.csv` | 雷角兽一行：race `monsters`、`HP 340` / `attack 30`、`技能 = 雷角电击`、`特殊机制` 写清“普攻攒能量、满后连续电击 3 秒”、`svg = thundercorn`、rarity `epic` |
| `data/brawl/roster.csv` | 一行（候战席、权重 3）⇒ 商店与胜局奖励里抽得到 |
| `scripts/core/loc_names.gd` | `piece.thundercorn` = 雷角兽 / Thundercorn |

**② 攒与花各只有一处**

| 谁 | 在哪 | 做了什么 |
|---|---|---|
| 攒 | `BrawlActor.charge_energy()` | **一次普攻一次存款**（`ENERGY_PER_STRIKE` = 10）。它在 `_begin_strike` 里、**四/五种形状之外**的那一行——所以射出去的箭、吞下去的人、挥出去的一刀都算，而**通道的跳数不算**（那是同一次attack在分期付款）。没有大招的行**一分不攒**（判据是第十道门 `brawl_ult_seconds`） |
| 花 | `BrawlActor._open_ultimate()` | 开火那一击照旧走 `land_hit`（伤害只有一个业主），随后把**剩下的**交给竞技场已有的通道 `BrawlBeam`——`Brawl.open_beam(..., ULT_TICK_SHARE)`。**这不是第五种attack形状**：它是这一行的 `远程特效` 被按住 |

- **每跳价钱不一样，是因为两种通道不是一回事**：`持续` 开的是**节奏**（眼球塔 3 秒烧掉三次attack的量，`BEAM_TICK_SHARE` 0.5），大招开的是**爆发**（`ULT_TICK_SHARE` 1.0 = 每跳一整下）。3 秒 = 开火 1 下 + 通道 5 下 = **6 下**，约等于它正常打 3 秒的三倍。
- **数在 `BalanceBrawl`**（`ENERGY_PER_STRIKE` / `ENERGY_MAX` / `ULT_TICK_SHARE`）：它们是**这个模式的规则**，与 `BalanceBattle.ULT_CHARGE_PER_CAST` / `ULT_CHARGE_MAX` 是同一个形状（一次攒多少、攒满要多满是**模式**的数，大招**是什么**才是行的数）。
- **不写第二张伤害表**：大招的每一跳都走 `land_hit`，所以狂暴、挂件、受害者的 `厚皮`、盾卫的击退**全都照旧生效**（§12 那条禁令在这里继续成立）。

**③ 能量条不是新画的东西：它就是大招条**（`Unit` 的 [P30-B] 那条，画在血条下面那格）

- `HumanPiece` 只回答那条 bar 问的四件事：**谁有**（`has_ultimate` = 行里的 `大招持续` > 0）、**攒多满**（`ult_charge_cap` = `ENERGY_MAX`）、**写什么字**（`ult_bar_text` = `60/100`——乱斗棋子没有 skills.csv 的大招行可念，而它真有的那个名字（`技能` 格）说的是普攻，写在这条 bar 上是说谎）、**攒在哪**（直接就是 `Unit.ult_charge`，**没有第二个计数器**）。
- 于是**两种模式的“正在攒大招”是同一条 bar**，而回合制那套充能事件够不到它：`ult_charge_source()` 答空串，所以挨打不会给它加分（`take_damage` 里那一行问的就是它）。
- ⚠ **`ult_code` 仍然是空的**：乱斗棋子的大招不是 skills.csv 里的一行，`ult_id` 也没有值——这正是四个覆写存在的理由。

**④ 两种新画法，都在既有的一族里**

| 画 | 业主 | 形状 |
|---|---|---|
| **雷击 `thunder`** | `BalanceUI.BEAMS` + `Fx._beam_thunder` | **折线**（七个折点，两端严格落在两个身体上）+ 两条分叉；折法是**相位与序号**的函数（没有 rng，同一击两次一样）。`phase_speed` 14 = 通道期间每秒重折 14 次，所以“持续电击”看得出是持续的 |
| **出手点 `muzzle`** | `BalanceUI.BEAMS` 每行一格 + `Fx.beam_muzzle(kind, box)` | 一条光默认从**身体中心**出去；雷角兽的雷**从角上出去**，所以那一格按**画框的比例**给（SVG 的 (16,16) 在 128 px 画布上 = `-0.375`，比例而非像素是因为乱斗会把棋子画大）。**一闪与通道共读**（`BrawlActor.muzzle`），所以一条attack只有一个出膛点 |

**⑤ 素材与朝向**

- `assets/svg/units/monsters/thundercorn.svg` 是**用户画好的**（黄身、左上角一只角、两只眼睛在左半边 ⇒ **朝左**）。⚠ 新素材要 `--import` 过一次才读得到；**没导入不等于报错**：`PieceDB.art()` 会在**同族**里回退到别人的图（雷角兽会穿着激光眼的画上场），这是这一族最容易骗过眼睛的一步。
- **画的朝向**由**单位自己的行**说了算（[B16] 起是 `units.csv` 的 `face` 列 → `Unit.faces_left`），它**不决定朝哪打**——棋子每一 tick 都转向目标，所以左右半场都对着敌人；它答的是“**这个身体是不是站在它这件模型天生不属于的半场**”（`BrawlActor.is_turned`）。
- ✅ **画本身会跟着翻了**（[B16] 落地，见 **§8.15**）：朝左的画摆在左半场时，身体被**镜像**，于是它和别的棋子一样看着敌人——[B4] 那条“身体会被镜像”的欠账就是这一笔。

**⑥ 已知缺口**：`thundercorn` 与另外五个怪兽一样**只进乱斗**（`turned = 0 / timed = 1`），而经典图鉴的种族按钮只有植物 / 僵尸 / 人类三页（§8.9 ⑥），所以**图鉴里仍然看不到怪兽这一页**。

### 8.14 遣散：把一枚棋子请出这一局【B15 已落地，2026-10-06】

**一句话：条带最左端那枚「遣散」按钮，把**手上**那枚棋子从名册里删掉——它戴的挂件全部回背包，
什么都不返还，且**最后一枚棋子不让你删**。**

用户原话：“为乱斗模式增加遣散棋子的按钮和功能。”

**① 一枚按钮，一条手势**

| 在哪 | 什么 | 谁给的矩形 |
|---|---|---|
| 条带**最左端**（`BrawlLayout.dismiss_rect()`） | 「遣散」`Button`（120 px，与「出战」同宽） | `BrawlLayout.compute_for()`：候选的起点改成**从遣散右边**算起，不是从棋盘左边缘 |
| 编排页（`_dismiss`） | 与候选、出战同一次 `_build()` 建出来，`_clear_entries()` 一起清 | `_layout_columns()` |

- **为什么在最左端**：条带的**两端是这一页的两件事**——左端扔棋子、右端开始这一轮（D67 的「出战钉在最右端」不动），
  中间三个候选照旧。破坏性动作与提交动作**隔得越远越好**，这是唯一的理由。
- **为什么由“手”武装**（`_sync_dismiss()`：`disabled = _selected < 0`）：遣散**不可撤销**，所以它要一个两步手势——
  先拿起一枚棋子（那枚棋子会戴上选中框，拿起的提示语 `brawl.form.selected_piece` 也点名这枚按钮），按钮才亮；
  空手时它是暗的（`disabled` 的底色由 `UiStyle` 给）。**这就是全部的安全措施**，没有二次确认弹窗。

**② 规则三条，全在 `BrawlSession.dismiss()` 一处**

1. **挂件先回家**：`attach_slots()` 里的每一行在棋子走之前 `bag.append()`（O36 说挂件从不锁死；
   棋子戴着三件走掉是这套功能唯一会**静默丢价值**的地方）。背包没有容量（O38），所以没有第二个“放不下”。
2. **最后一枚拒绝**：`pool.size() <= 1` ⇒ false。名册空了就**永远无法上场**（竞技场见到空半场当场判负），
   而这一页没有别的办法把棋子找回来。页面用一句话说明（`brawl.form.dismiss_last`），不是让按钮默默不动。
3. **什么都不返还**：见下条。

**③ 它不是“出售”：`O47` 仍然未决**

- 用户点的是**遣散**（把棋子请走），不是**出售**（换钱）。两者的区别就是**返还**，而返还属 D4 那一层经济，
  D71 当初正是为了这件事把整枚按钮推迟的（O47）。⇒ **这一批只做“请走”，不动经济**：`coins` 一行没改。
- 还有一条反对全额返还的理由：一枚棋子可能是**胜局奖励白拿的**，按商店价（`费用 × PIECE_PRICE_PER_COST`）卖回去
  就是一台金币水龙头。真要做出售，规则应当连**来源**一起考虑，那是 D4 的问题。

**④ 表与自检：这一批一格数据都没加**

- 没有新列、没有新素材、没有新 `class_name`、**没有自检模块**（AGENTS §2）。
- 开机读数是**日志**：每遣散一次打一行 `[Brawl] dismissed militia (wearing 2) - 5 piece(s) left, bag 3`。
- ⚠ **索引会挪**：`pool.remove_at()` 之后，**它后面的每一枚棋子的下标都减一**。所以页面在调用**之前**把
  名字与挂件数读出来，调用**之后**把两只手都清掉（`_cancel_drag()` + `_selected = -1`）——这是这套改动里
  唯一一个“顺序写错就会遣散错人”的地方。

**⑤ 没做的**（登记在 `docs/OPEN_ITEMS.md`）：把棋子**拖到按钮上**遣散（TFT 那种拖去出售区的手势）今天不做——
一枚不可撤销的按钮有一条手势已经够了；真要加，是 `_drop()` 里的一处命中判定。

### 8.15 朝向写在表里，站位不同就镜像【B16 已落地，2026-10-06】

**一句话：一个单位**画**朝哪边是它自己的事实（`units.csv` 的 `face` 列 → `Unit.faces_left`），
而**站在哪个半场**是布阵的事实——两者不一致时，**身体被镜像**，于是它看着敌人。**

用户原话：“为units.csv增加新列face，表示朝向，默认朝向右侧，默认值可以为''，'1'，'r'，'right'。
像雷角兽朝向左侧，而玩家朝向右侧。像这样朝向不同时要反转朝向。把这个机制作为单位的基本机制写入代码。”

**① 一格数据，一条链（四个业主，各管一段）**

| 谁 | 在哪 | 管什么 |
|---|---|---|
| 表 | `data/units/units.csv` 的 **`face`** 列 | 这个单位的画**朝哪边**。写法是一个**封闭清单**：`r` / `1` / `right` / `右` = **朝右**（默认，也是全部现有素材的画法），`l` / `0` / `-1` / `left` / `左` = **朝左**；**空白 = 去问种族 `default` 行**（照 D80 的老规矩），默认为空时**代码兜底是朝右**，写错一个词会记一条 complaint 并按“朝右”读（响而不用命） |
| 行的读者 | `UnitSheet.face_left(id, 兜底)` | 唯一把“那个词”变成“哪一边”的地方（`defence()` 的同款门）。**兜底是家族自己给的**：僵尸传 `true`（它的手臂天生朝左），植物与棋子传 `false`（朝右） |
| 身体 | `Unit.faces_left` + `Unit.drawn_left()` | 出生时读一次（和 `defence` 一样在 `apply_type` / `apply_piece` / 五个植物基类的 `setup_*` 里各一行），此后**每帧只读字段**，不再问表 |
| 布阵 | `BrawlActor.is_turned()` → `Unit.mirrored` | **站错了半场就把画翻过去**：`mirrored` 是身体上的一个开关，四个 art 层级都认它（贴图走 `_draw_body` 的画布变换，视图场景走 `BodyPivot` 的 x 缩放） |

- **四个 case 一次说清**（左半场 = 玩家，右半场 = 敌人）：

  | 谁 | 画朝 | 站哪 | 镜像？ | 看起来 |
  |---|---|---|---|---|
  | 玩家的雷角兽 | 左 | 左半场 | **是** | 朝右（看着敌人）✔ |
  | 玩家的激光眼 | 右 | 左半场 | 否 | 朝右 ✔ |
  | 敌人的激光眼 | 右 | 右半场 | **是** | 朝左 ✔（**这一条是本批顺手修好的老毛病**：以前它背对玩家） |
  | 敌人的雷角兽 | 左 | 右半场 | 否 | 朝左 ✔ |

**② 为什么“朝向”与“瞄准”是两件事**

- `faces_left` / `drawn_left()` 说的是**这张画**；`facing` / `facing_dir()` 说的是**这个身体此刻瞄哪**——
  乱斗的棋子每一 tick 都转向目标（§5 的状态机），所以**瞄准永远是对的**，会错的只有画。这一批修的就是画。
- ⇒ **`mirrored` 是身体上的一个开关，不是画师的事**：`Unit` 自己决定怎么把自己的画翻过来
  （贴图：`_draw_body` 里那个同事先给“前倾”用的 `draw_set_transform` 多带一个 `-1` 的 x 缩放，
  画完立刻还原，所以**名字 / 血条 / 大招条不会跟着翻**；视图场景：翻的是 `BodyPivot`，不是 `view`）。
- ⚠ **不要用 `scale.x = -1`**：`play_death()` 会补间 `unit.scale`，而乱斗的“肚子里”姿态（§8.11）也在写它——
  镜像写在那里会被两者之一悄悄抹掉。这是本条最贵的一条经验。

**③ 出手点也跟着翻**（[B14] 的 `muzzle` 是**按画**给的）：

雷角兽的雷从**画的左上角**那只角出去，所以身体一翻，那只角就跑到右上方去了——
`BrawlActor.muzzle()` 因此在 `unit.mirrored` 时**把偏移的 x 取反**（一处符号，一闪与通道共用）。
不翻的话，雷会从后脑勺射出来。

**④ 这一批顺手做的事**

- `units.csv` 的 `face` 列**没有第二份**：`[B14]` 在两张族表里加的 `朝向` 列**已经删掉**，`PieceDB` 的读取与 `HumanPiece.drawn_left()` 的覆写一起退休——同一个事实两个业主，正是 `AGENTS.md` §2 禁止的。
- 四个 `default` 行**把默认写出来了**：`默认植物` / `默认人类` / `默认怪兽` = `r`，**`默认僵尸` = `l`**（僵尸整族朝左，这是它的画法，写一次就够）。
  于是**除僵尸外的一切都靠默认链回答**，没有一行需要改；只有雷角兽自己写了 `l`。
- 开机读数 `[Data] units: … | turned N, timed N, defence N, face left N` 多了一个 **`face left`**：
  它是“**有多少行说自己朝左**”（今天 **44** = 43 行僵尸 + 雷角兽），也是**拼错一个词时唯一会立刻叫出来的地方**
  （`status_text()` 会走遍每一行）。⚠ **同一行里 `filling N cell(s)` 的那个 N 会涨 109**：
  四个 `default` 行现在都给了 `face`，于是**除雷角兽之外的每一条单位行**都被默认链填了一格——
  那是**预期**，不是多出来的错误（上一批 `朝向` 只填了 11 格，因为它只写在两张族表里）。

**⑤ 预览也镜像了【B16b 已落地】**：编阵页画的是**图标**（`UiStyle.draw_icon`，不是 `Unit`），
而它现在**按同一套规则翻转**——四个地方：**左半场**（自己摆的棋子）、**右半场预览**（敌阵）、
**候战区**（那是玩家的棋子，按它将站上的半场预览）、**拖动时跟着指针的那具身体**；
商店 / 奖励 / 图鉴的图标**不翻**（卡片不是站在场上的身体，那里画的是素材本来的样子）。

- **共用一条规则，不抄一份**：`is_turned()` 拆成 `BrawlActor.turned_in(画朝左?, 哪个半场)` 这个**静态门**
  （实例版就是它加一句 `unit.drawn_left()`），页面用 `UnitSheet.face_left(id)` 拿到“这一行的画朝哪边”（**和身体出生时读的是同一个门**）再问它。

  **[S4/D70] 记分板那一半已经落地**：双方剩余 / 计时 / 倍速 / 狂暴 / 按键写在**共享顶栏**上（与编排页同一个矩形、
  同一个画师）；**还缺**暂停与倍速的**按钮**、击杀飘字、结算盖层（B4）。
  `hud.gd` 的性质有利：它 39 处读数**全走 `board.xxx()` 的门、对 `game` 的引用是 0 处**，
  所以乱斗 HUD 是"同一套绘制风格的另一条排版"，不需要把 `hud.gd` 撕开。

#### 10.1 观众 HUD 到底是什么（O46 里问的那件事）

**"观众" = 玩家在乱斗里扮演的角色**（§1：玩家不指挥战斗里的任何一只手，他只看）。
**观众 HUD = 竞技场屏幕上那块给"看的人"看的记分板**。逐条对一下现在有没有：

| 元素 | 现在有没有 |
|---|---|
| **双方剩余棋子数**（左 n : 右 n） | ❌ 只在结算时报进日志 |
| **倒计时 / 已用时间**（2 分钟、超时狂暴第几级） | ❌ 只有 `RAGE n` 那一行日志 |
| **暂停 / 倍速按钮**（`SPACE` / `F` 的鼠标版） | ⚠ 键有（D15），**屏幕上没有按钮**，也不显示当前倍速 |
| **击杀播报 / 飘字** | ❌ 只有 `[Brawl] 12.3s LEFT piece down` 的日志行 |
| **结算面板** | ⚠ 有**结算页**（打完切页），但**场上不盖一层** |
| **血条** | ✅ 棋子自带（`Unit` 那一层共用） |

⇒ 它现在是一条**"用控制台当 HUD"** 的临时状态：`brawl.gd` 的 `_input` 有四个键、日志有读数，
但屏幕上除了棋子本身什么都没有。这正是 B4 里"观众 HUD"那半件事，也是 O46 问到的那个词。
（`hud.gd` 的 39 处读数已经全部走门，所以做它主要是**排版**工作，不是接线工作。）

#### 10.2 版面与预算（S1–S4，2026-10-05；数字都能复核）

**业主**：`scripts/core/brawl/brawl_layout.gd` 的 `BrawlLayout.compute_for(logical_size)`。两页都读它——
`BrawlField.arena_rect()` 就是 `BrawlLayout.board_rect()`，顶栏是 `BrawlHUD.draw_top_bar`——而 `Layout`（回合制）
与它**互不引用**。**`cell` 只出一个数**：棋盘 = `cell × (9, 5)`，其余全是它的份额。

**为什么棋盘一直大不起来**：棋盘 9:5 = **1.8 : 1**，16:9 = **1.78 : 1**，两个比例几乎相同 ⇒ 两轴的余量
同时见底。旧版把棋盘摆在 `Layout.lawn_rect()` 上，等于替回合制付了 **左 160（脑子区）+ 右 176（卡槽留白）+
上 100 + 下 120** 的 chrome，而乱斗一件都用不上；那 336 px 横向 chrome 还被编排页的两个侧栏占着，
所以"把东西从一处搬到另一处"永远只涨几点。这一版做的是**删 / 并 / 摊**：右栏删掉（候选摊进带里）、
顶带压到 48、背包收成一列、候战排按 cell 计价。

**算式（1280×720，`c` = cell）**：

```
竖向：2×8 边距 + 48 顶栏 + 6 + 5c 棋盘 + 4 + 0.72c 候战排 + 4 + 46 带 ≤ 720
      ⇒ 5.72c ≤ 596 ⇒ c = 104      （棋盘 936×520 = 屏面 53%）
横向：2×8 边距 + 64 背包列 + 12 + 9c 棋盘 ≤ 1280 ⇒ c ≤ 132（16:9 下不是墙）
```

| 窗口 | cell | 棋盘 | 占屏 | 墙在哪 |
|---|---|---|---|---|
| 16:9 1280×720（设计档） | **104** | 936×520 | **53%**（旧 45%） | 竖向 |
| 4:3 1280×960 | **132** | 1188×660 | **64%**（旧 44%） | 横向（9c 撞满可用宽） |
| 5:4 1280×1024 | 132 | 1188×660 | 60% | 横向 |
| 21:9 1680×720 | 104 | 936×520 | 43% | 竖向（棋盘追不上 2.33 : 1） |

⇒ 收益最大的是**竖一点的窗口**（4:3 从 44% 跳到 64%）：右栏没了之后，横向**第一次不再是墙**。
16:9 只涨 8 个 cell（面积 +18%），这是几何决定的（棋盘与窗口同比例），不是实现问题。

**顶栏四槽写什么**（D70）：编排页 = 标题 / 上阵数与金币与候战区 / 按键提示 / 对手（D34 的三项）；
竞技场 = 双方剩余 / 计时与倍速与狂暴 / 按键 / 本轮与对手。

**还没做的两条**（见 §11 的 O47 / O48）：格子**不等边**（`c_w ≠ c_h`，能再换 ~7%，代价是改写"唯一尺寸"
这条与 D11 / D14 两处按格计的判定）、chrome 做成**浮层**压在无人区上（16:9 能到 64%，代价是遮挡可点格子）。

#### 10.3 经典模式的图鉴（D75–D77）

**它在哪**：经典模式的主菜单上，地板上那本**书**（D74）——同一个物件在两个 shell 里各开各的页
（`MainMenu._on_almanac()` 按 `SettingsStore.ui_shell` 分流，路由的业主是 `Game.show_brawl_almanac()`）。

**它读什么**（每一页都只有一个数据业主，页内不发明数字）：

| 页签 | 数据 | 读法 |
|---|---|---|
| **单位** | `data/units/units.csv` 的 `timed` 列 | `UnitSheet`（唯一的花名册读者）+ 各种族自己的层（`humans.csv` 的费用 / attack距离 / 移速 / attack间隔 / 射弹、`zombies.csv` 的护甲 / 移动 / 啃脑伤害） |
| **挂件** | `data/brawl/gear.csv` | `GearDB`（强化与装备同表，D46） |
| **敌阵** | `data/brawl/formations.csv` | `FormationDB`（棋子数 / 战力合计 / 奖励，D34） |

**种族那一行是三个按钮**（植物 / 僵尸 / 人类）：回合那页只有两个，所以这一页在 `_layout()` 里**自己重新居中**
（基类的 `metrics_for` 按 `ALMANAC_RACE_COUNT` 算，两个），并把**道具分组那一行整行藏掉**（那是回合模式的四种道具分类）。

**它不显示什么**：没有关卡包（经典模式的"关卡"就是敌阵）、没有 `data/items.csv`（那是回合模式的道具）。
一个种族今天在经典模式里没有单位时，格子是空的、面板照常说话——**空页是数据说的话，不是页面的 bug**。

**两个模式共用的第四页签 = 射弹图鉴（D78）**：`data/projectiles.csv` → `ProjectileDB`。
它**住在基类 `AlmanacView` 里**（回合那页），经典那页的四条缝（`_section_title` / `_read_rows` /
`_detail_lines` / `_description`）在**不属于自己的页签上一律 `super`**——所以"射弹长什么样"在这份仓库里
只有一处实现（`grep ProjectileDB scripts/ui` 应当只命中 `almanac.gd` 与那个模块自己）。
面板的六行读 `ProjectileDB` 的门（`pierce_of` / `bounce_of` / `splash_of` / `armor_piercing` 是 [D78] 新开的），
**右上角的图不是贴图而是画出来的**：`Projectile.draw_shot()` —— 与回合制的弹道、乱斗的自由飞行**同一个画师**。
**画什么由表决定（D79）**：`贴图` 列填了就画那张 SVG，没填就画图元；**格子、面板与战场读的是同一个 `ProjectileDB.art_of()`**
（格子那一格由此有图——`ItemTile` 现在**按图片自身比例**放进方形格子，方形图（全部单位/道具/关卡）一个像素没动，只有五比一的箭这种非方图受了影响）。
画框 104 px 而豌豆只有 14 px，所以面板**按 `Projectile.draw_extent(look)` 放大到画框的 ~70%**（`p_scale` 默认 1.0，
两个引擎都不传 ⇒ 场上尺寸一个像素没变）——**放大的是同一张画，不是另画一张示意图**。

## 12. 与回合制模式的关系（边界）【D10】

**共用的是"棋子能做什么"，分家的是"棋子想做什么、什么时候做"。**

```
素材/数值层   表 + DB + Balance*                    ← 两种模式共用（已经分好）
     │
棋子层        Unit / Zombie / 植物脚本 / Projectile
              HP / 伤害 / 护甲 / 处决 / 状态 / 大招 / 死亡账 / 贴图   ← 共用，且不许有第二份
     │
     ├──────────── 回合驱动 ────────────┐┌────────── 实时驱动 ──────────┐
     │  battle.gd（Phase 机 / AP / END TURN / 脑子）  ││  brawl.gd（时钟 / 意图 / 寻路避让 / 团灭） │
     │  会话编排 battle_main.gd                        ││  会话编排 brawl_main.gd（⏳ 未建）        │
     └───────────────────┬───────────────────────────┘└──────────────┬──────────────────────────┘
                     Game（组合根 + 前端 + 存档）——按需分派，两个会话互不认识
```

- **分家（本来就该有两份，因为它们是两个不同的事实）**：
  **意图**（回合的僵尸意图是"前方一格有植物就啃"，`battle.gd` 的 `_decide_zombie_act()`；乱斗的意图是"最近的敌人、保持间距、绕开障碍"）、
  **时钟**（`Phase` 机 vs 定步长 tick）、**胜负**（脑子/入场表出完 vs 团灭/超时）、**场地语义**（行=泳道 vs 自由二维）。
- **不许做的**：在 `battle.gd` / `zombie.gd` 里写 `if brawl:` 的分支；抄一份伤害/护甲/处决规则到乱斗里。
  `scripts/core/arch_check.gd` 那条"两个文件不许声明同一个名字"的判据就是为这件事准备的，
  ⏳ 建议把它从 `battle ↔ game_manager` **扩成也管 `battle ↔ brawl`**——让"抄一份"变成开机可见的 FAIL。
- `Game` 的职责不变：**开一个会话、注入句柄、收它的信号、存它的账**。
  乱斗会话的上下界照 `battle.gd` 头部那张 DOWN/UP 表写（`begin` / `cancel` / `settled` / `left` / `settings_requested`），
  这样 `front_end_flow` 与设置页**不用为乱斗写第二套**。

## 14. 自检与验收（形状；命令归 `docs/DEV.md` §2）

实时系统最容易变成"只能靠眼睛验收"，这个工程不接受那种东西。三条底线：

> ⚠ **[B1–B2c] 现状：这三条现在只有人眼，而且以后也只有人眼。**
> 用户 2026-10-04 先要求"像 `arch_check` 这种测试文件就不要编写了，我手动测试后反馈"，
> 又在那天晚些时候把这条**升格成全工程规矩**："不要编写测试脚本，即使是临时探针也不行"
> ⇒ 归 **`AGENTS.md` §2 的"不写测试脚本"**（连 `[Brawl]` 判据在内，**一条都不补**；
> AI 也不跑验收，命令由用户跑、结果由用户反馈）。
> 上面那三条底线因此**降格为"人的验收清单"**：它们是"你自己测的时候该看哪三件事"，
> 不是"等谁写出机器判据"。这一批的三个坑（`start_bout()` 参数、`apply_language()` 门不存在、
> 敌阵贴图问错花名册）都是**手动测出来**的，记在 `docs/PITFALLS.md` §2.1。

1. **定步长**：逻辑步长固定，`--quit-after` 那套照样能跑；无头 10× 快跑与 1× 的**摘要必须逐字相同**。
2. **种子化**：同一颗种子跑两遍，结果（用时 / 双方剩余 / 击杀 / 总伤害）**逐字相同**。
3. **不变量**：跑满一整轮，断言"没有棋子卡死超过 N 秒"、"双方真的交过手"、"团灭在时限内发生"。
   再加一条**性能读数**：每 tick 的耗时预算（把"实时跑不动"变成开机可见的数字，而不是玩家的卡顿）。
